# PeaceLocker 2.0 — Rust Rewrite Roadmap

**Status:** Proposed implementation plan  
**Strategy:** Complete rewrite on a separate branch  
**GUI:** egui/eframe  
**Target:** Windows-first Rust desktop application

## 1. Delivery strategy

Build PeaceLocker 2.0 as a new application while keeping the C++ implementation intact as a reference and migration source.

Do not begin by translating the legacy files one by one. Establish the security model, core contracts, storage format, and task lifecycle first. Build monitoring and GUI features on top of those stable foundations.

Recommended Git strategy:

- Keep `main` as the legacy baseline until the project owner chooses otherwise.
- Use a dedicated implementation branch such as `rewrite/rust-v2`.
- Keep architecture/security/roadmap decisions in `docs/`.
- Use small, reviewable commits.
- Add an Architecture Decision Record (ADR) when a decision changes a security boundary, persistent format, or platform dependency.

The documentation branch for this specification is separate from the eventual implementation branch.

## 2. Milestone overview

| Phase | Milestone | Depends on | Exit condition |
|---|---|---|---|
| 0 | Workspace foundation | None | Clean Windows build, CI, crate boundaries |
| 1 | Security foundation | Phase 0 | PIN, key protection, AEAD tests pass |
| 2 | Encrypted storage and migration | Phase 1 | Versioned store and safe migration work |
| 3 | Core state, commands, and rules | Phase 0–2 | UI-independent domain engine works |
| 4 | Monitoring sources | Phase 3 | Process/Explorer/browser sources report health |
| 5 | Event and notification services | Phase 3–4 | Bounded, cancellable event pipeline |
| 6 | Modern GUI | Phase 1–5 interfaces | Usable desktop app connected to core |
| 7 | Windows integration | Phase 4–6 | Tray/startup/single-instance lifecycle works |
| 8 | Hardening and release | All previous phases | Tested installer and release candidate |

Phases may overlap where interfaces are stable, but do not start UI feature work against unsettled security/storage APIs.

## 4. Phase 1 — Security foundation

### Tasks

- [ ] Define typed security errors.
- [ ] Define versioned PIN verifier structure.
- [ ] Implement Argon2id hash/verify with unique random salts.
- [ ] Bound and validate stored Argon2 parameters.
- [ ] Benchmark parameters on representative supported hardware.
- [ ] Implement secure random generation for DEK and recovery codes.
- [ ] Implement DPAPI protect/unprotect wrappers.
- [ ] Define the data-key lifecycle.
- [ ] Implement AEAD envelope using a maintained implementation.
- [ ] Define nonce generation/uniqueness policy.
- [ ] Define authenticated associated data.
- [ ] Implement single-use recovery code verification.
- [ ] Implement lockout policy and persistence contract.
- [ ] Add secret-redaction helpers for logs.
- [ ] Add unit and property-oriented tests for malformed inputs and tampering.

### Acceptance criteria

- Correct PIN verifies and incorrect PIN does not.
- PIN is never stored or logged.
- Salts are unique and generated by a cryptographic RNG.
- AEAD tampering fails closed.
- DPAPI failure does not trigger plaintext storage.
- Recovery codes are single-use.
- Key and verifier format versions are explicit.
- Security tests run in CI where supported; Windows-specific DPAPI tests run on Windows.

### Deliverable

A security crate that can be tested independently from the GUI and monitor engine.

### Acceptance criteria

## 7. Phase 4 — Monitoring sources

Implement sources incrementally. Each source must report whether it is supported, initialized, degraded, or unavailable.

### 4A. Process monitoring

- [ ] Implement documented process enumeration/query APIs.
- [ ] Track PID and process lifetime identity.
- [ ] Handle PID reuse.
- [ ] Distinguish access denied, exited, and query failure.
- [ ] Add configurable sampling/backoff where polling is required.
- [ ] Prefer event-based process notifications where reliable.
- [ ] Implement process rule matching.
- [ ] Test process start/exit and race conditions.

**Acceptance:** matching and non-matching process scenarios work; source failures are visible; no false healthy status.

### 4B. Explorer location monitoring

- [ ] Implement a Windows Explorer source behind an interface.
- [ ] Define COM apartment/thread ownership.
- [ ] Handle Explorer restart and window lifecycle changes.
- [ ] Normalize observed paths.
- [ ] Handle unavailable or inaccessible windows.
- [ ] Add source health and diagnostics.
- [ ] Document that this is observation, not filesystem access control.

**Acceptance:** Explorer navigation events are normalized; COM failures do not crash the application; limitations are visible.

### 4C. Browser URL detection

- [ ] Define browser adapter contract.
- [ ] Implement URL normalization and parsing.
- [ ] Select initial browser support based on testability.
- [ ] Implement UI Automation on a correctly managed COM thread.
- [ ] Handle browser version and accessibility-tree changes.
- [ ] Handle missing browser, background tab, and inaccessible UI cases.
- [ ] Add tests for URL matching and normalization.
- [ ] Document best-effort detection limitations.

**Acceptance:** supported test cases pass for each declared browser; unsupported conditions are surfaced; no universal blocking claim is made.

### Process suspension decision

Do not port `NtSuspendProcess` as a core requirement. If retained experimentally, isolate it behind a clearly labeled adapter and test resume/failure behavior. It must not be described as robust security enforcement.

### Deliverable

A monitoring crate with independently testable sources and clear health reporting.

## 12. Suggested first sprint

The first sprint should produce the foundation and the first security proof-of-concept, not the entire feature set.

1. Create the Rust workspace.
2. Pin the toolchain and dependency versions.
3. Add CI for formatting, Clippy, tests, and Windows build.
4. Create core/security/storage/Windows crate skeletons.
5. Define typed error boundaries.
6. Implement Argon2id verifier generation and verification.
7. Implement DPAPI protect/unprotect wrapper on Windows.
8. Implement a minimal AEAD envelope round-trip.
9. Add tests for wrong PIN and ciphertext tampering.
10. Launch a minimal egui window.

Sprint exit criteria: the app launches, the workspace checks pass, and the security proof-of-concept passes automated tests on Windows.

## 13. Project conventions

- Use descriptive module and type names.
- Prefer explicit types over stringly typed state.
- Avoid `unwrap()` and `expect()` in production paths unless the invariant is documented and truly unreachable.
- Do not introduce `unsafe` without a narrow wrapper, safety comment, and tests.
- Keep unsafe Windows FFI in the platform crate.
- Do not commit generated binaries or local build outputs.
- Do not commit real webhook URLs, keys, PINs, recovery codes, or user data.
- Keep `Cargo.lock` for the application workspace.
- Run formatting, Clippy, and tests before each milestone commit.
- Document every persistent format change.
- Prefer small commits with one coherent purpose.

## 14. Risks and mitigations

| Risk | Mitigation |
|---|---|
| UI Automation changes across browsers | Adapter design, declared browser support, best-effort wording |
| COM thread-affinity bugs | Dedicated correctly initialized apartment/thread |
| Weak PIN entropy | Argon2id, longer PIN/passphrase guidance, lockout |
| DPAPI context changes | Explicit user-scope behavior, recovery and migration tests |
| AEAD nonce misuse | Reviewed library and explicit nonce strategy |
| Background task leaks | Supervision, cancellation, bounded queues |
| Overly broad monitoring | Opt-in settings and data minimization |
| Privilege creep | Normal-user process by default; separate review for elevation |
| Legacy format incompatibility | Read-only inspection first, backup, controlled migration |
| Scope expansion into true vault | Separate product feature and threat model |

## 15. Completion criteria

PeaceLocker 2.0 is ready for release only when all of the following are true:

- [ ] The Rust application builds and runs on supported Windows versions.
- [ ] The modern GUI is connected to real application state.
- [ ] Authentication and recovery pass tests.
- [ ] Configuration is encrypted and authenticated.
- [ ] Key protection uses DPAPI without plaintext fallback.
- [ ] Monitoring sources expose accurate health and documented limitations.
- [ ] Rules engine is independent of GUI and Windows API implementation.
- [ ] Notification queues are bounded, cancellable, and rate-limited.
- [ ] Privacy-sensitive features require explicit opt-in.
- [ ] Background tasks stop cleanly.
- [ ] Migration is backed up, validated, and recoverable.
- [ ] Installer and uninstaller pass clean-machine testing.
- [ ] CI checks pass.
- [ ] README, architecture, security, and known-limitations documentation match the shipped implementation.
